# 为什么需要数据流芯片

## 数据流架构芯片是什么

**定义**：数据流架构，就是由数据驱动执行的计算架构。当一个计算节点所有的输入数据都准备好了，就可以立刻开始执行，而不需要受 PC 或其他控制单元的控制。

**核心机制**

核心机制主要包括数据令牌和点火规则：

- **数据流图**：数据流程序通常会被表示为一个数据流图。其中的节点代表运算（例如加减乘除、矩阵乘矩阵、向量乘等），边则代表数据依赖。
- **数据令牌**：数据会以令牌的形式在边上流动。
- **点火规则**：当一个节点所有输入边上的令牌都准备好时，该节点就可以开始点火执行。执行时会消耗输入边的令牌，并产生新的输出令牌，沿着输出边传给下游节点。

## 从编译到执行

### 编译阶段

在编译阶段的过程中，其中一个中间产物就是上述抽象的数据流图。

经过 **Lowering** 之后，数据流图中的节点会被对应至芯片中的 tile，边会被映射到 NoC 路由路径。

数据流架构芯片的编译器，往往会在编译处理阶段就定义好：

- 每一个 tile 都应该计算什么；
- 它的前置数据依赖是什么；
- 它输出的数据应该传至哪一个 tile。

### 芯片执行过程

对应到芯片上的执行过程：

1. Host 端将输入数据搬运至 GDDR6；
2. NoC 网络将其搬运至编译时就确定好的 tile 上；
3. 对应的 tile 在满足点火规则时开始进行运算；
4. NoC 将输出数据传递至下一个编译阶段就确定好的 tile 上；
5. 直到下一个 tile 满足点火规则，重复此过程。

---

其实这里还遗留了一个有意思的问题，也就是在芯片的硬件层面，他们是怎么判断计算节点当前是否满足点火规则的？这个其实会在后续的数据流芯片技术分支的那一章来进行说明。

通过以上计算和测试数据，可以知道为什么大家一直在说，Decode阶段才是大模型推理的主要瓶颈。不仅是带宽受限的问题难以解决，更在于目前主流GPU中，Decode在推理阶段的时间占比接近99%。


## 为什么数据流架构可以解决 Decode 瓶颈

本质上，我们要解决 Decode 阶段的两个问题：

1. **计算单元闲置**
2. **带宽利用率极低**

在 NVIDIA GPU 中，数据需要从 HBM 搬到 L2 Cache，再搬到 L1 Cache，最后搬到 Register，才能到达计算单元。有以下几种解决方案：

### 第一种：权重驻存

Google TPU 的做法是把权重拆分成多份，分别常驻在多个 Tile 的 SRAM 上（局部存储）。对于小模型可以全部常驻，对于大模型则采用分级策略：能常驻的常驻，不能常驻的分块流式加载。

SRAM 的读写带宽远高于 HBM 和 DDR，且读写都可以在一个时钟周期内完成，确定性较强。但价格昂贵，容量有限。

### 第二种：计算与通信并行化

GPU 通过 SIMT 掩盖内存读写延迟，但当线程数较少时（如 Batch=1），这种掩盖就会失效。数据流架构天生就是计算与通信并行：当一个 Tile 正在计算时，其所需的数据会在 NoC 网络上同时传播。数据到达即触发下一级计算，不需要等待全局同步。

### 第三种：完全软件定义的数据流

编译器可以完全根据当前运行的负载，对数据流图进行深度优化，省去硬件层面的调度、同步等开销。CPU 和 GPU 的调度和控制主要由硬件动态完成（如乱序执行、warp 调度、缓存替换），软件只能间接影响，无法精确控制每一个数据的流动路径和时序。而数据流架构的编译器可以做到编译时静态调度，行为确定，延迟可预测。

### 额外思考

- **能耗优势**：减少外部内存读写，减少冯·诺依曼架构中控制部分的开销。
- **Batch=1 场景更优**：不依赖线程数掩盖延迟，数据流动本身就是并行。
- **硬实时性**：静态数据流架构的延迟可预测，适合自动驾驶、机器人控制等场景。
- **局限性**：灵活性差、编译难度高、SRAM 成本高、大模型必须分块，甚至说要是做多级存储例如，只把当前需要参与运算的权重放在SRAM中，不需要参与的权重放在DDR中，由编译器决定什么时候SRAM和DDR中的权重要进行互换。
- **未来**：3D堆叠芯片目前正在蓬勃发展，已经有一些厂商开始尝试堆叠SRAM。这意味着数据流架构芯片可以在片上拥有更多存储空间，运行数量更大的模型。
