# 从大模型推理的物理本质看计算范式变革：为什么需要数据流芯片？

## 引言：算力需求的结构性转移

过去十余年，深度学习训练与高吞吐推理主要由 SIMT GPU 承担。进入大语言模型（LLM）时代后，工程重心从“万卡预训练”进一步扩展到“线上自回归推理”，其中 Decode 阶段往往占一次请求的大部分时间。此时系统瓶颈不完全由峰值 FLOPS 决定，而更多受“每次生成要搬多少参数、用多大带宽搬”约束。


## 一、大模型推理的底层物理特征

### 1.1 Prefill 与 Decode 的两阶段割裂

LLM 一次请求通常分为：

- **Prefill**：把 Prompt 的 N 个 token 一次性前向，建立 KV Cache，并输出第一个新 token。计算以长序列 Attention 与 Dense GEMM 为主，批内 token 越多，权重读次越能被摊薄，算术强度高，整体更接近 Compute-Bound。
- **Decode**：自回归逐个 token 生成。每步只对当前 1 个新 token 做前向，但要读全部权重；Attention 还要读已存 KV。单步计算量相对小、访存量相对固定，小 Batch 下接近 Memory-Bound。

用 Roofline 的算术强度近似：若 Batch=1、FP16 全量读权重，Decode 权重侧算术强度约为

```text
I ≈ 2P / 2P = 1 FLOP/Byte
```

其中 P 为参数量，每个参数 2 字节、前向约 2 FLOP/参数。Prefill 因为一次处理 N 个 token，同样权重可被 N 个 token 的计算分摊，强度随序列与批大小上升。

以 H100 SXM 为例做脊点对照：NVIDIA 数据表给出 H100 SXM 80GB HBM3、内存带宽 3.35TB/s；TF32 Tensor 峰值 1000 TFLOPS，FP16/BF16 Tensor 2000 TFLOPS（含稀疏），FP8 4000 TFLOPS（含稀疏）。 若用 dense FP16 非稀疏峰值约 989 TFLOPS 做教学估算，脊点：

```text
I* = 989 TFLOPS / 3350 GB/s ≈ 295 FLOP/Byte
```

Batch=1 Decode 若只有约 1 FLOP/Byte，明显低于脊点，属于带宽受限区。 该数字是用官方峰值和带宽反推的教学值，不等于某模型实测 MFU。

### 1.2 低 Batch 场景成为主流刚需

- **个人/工作站推理**：单用户、单会话，Batch 常接近 1，难以靠合批摊薄权重读取。
- **端侧实时控制**：智驾 VLM/世界模型、机器人决策要求感知—规划—控制闭环在十几到几十毫秒级；Batch=1 更常见，且要求长尾抖动可控。
- **全双工语音与实时视频**：人类对话停顿感知在几百毫秒级，扣除 ASR/TTS/网络后，留给 LLM 的首字与逐字预算很紧。
- **长链推理 Agent**：若单流生成太慢，长 CoT 会放大等待时间；提升单流吞吐可由更大带宽、更低精度、投机解码、更优调度共同实现，而不是单靠堆 FLOPS。

结论：当产品要求“单流低时延”而非“多请求合批吞吐”时，Decode 的访存带宽与确定性问题会比 Prefill 的峰值算力更突出。

## 二、传统 GPU 的适应性危机与自我演进

### 2.1 小 Batch Decode 下的三类问题

**1）延迟掩盖依赖大并发。**  
GPU SIMT 靠大量 Warp/线程级并行掩盖 HBM 访存延迟。Batch=1 或极小 Batch 时，可调度线程少，HBM 高延迟不能被充分隐藏，计算单元更容易空等。 这是架构特性，但是否“严重空转”取决于模型大小、精度、内核融合、KV 大小与运行时。

**2）小 Batch Decode 的 MFU 天然低。**  
MFU＝实际模型 FLOPs÷峰值 FLOPs。第三方推理经验区间显示：Prefill 在良好融合内核下可到 30%–50%；Decode 在较大 Batch（如 32）受带宽限制可能只有 8%–12%；更小 Batch 会更低。 对 70B FP16、Batch=1，仅按全量读权重估算：权重约 140GB，H100 SXM 3.35TB/s 全读理想下限

```text
t ≥ 140 / 3350 ≈ 41.8 ms/token
```

对应理想最多约 24 tok/s；计入 KV 读取、Attention、内核与通信开销，第三方教学估算实际约 15–20 tok/s。 这不是“GPU 差”，而是小 Batch 全精度 Decode 的带宽下限问题。

**3）控制与搬运能耗不可忽视。**  
通用流水需要取指、调度、寄存器、多级缓存；片外 HBM 搬运能耗远高于片上计算。该定性广泛使用，但具体“DRAM 一次搬运是 16bit 加法的 100–200 倍”应标注为经典工艺/电路估算，不等同于某芯片现网能效。更稳妥写法是：在先进节点，大容量片外访存通常比片上近存计算更耗电，因此近存/片上 SRAM 架构在能效上有结构优势，但优势幅度高度依赖模型、精度与利用率。

### 2.2 GPU 自己的演进与剩余矛盾

NVIDIA 面向推理持续迭代：H100 支持 FP8 Transformer Engine、较大 HBM3 带宽、MIG、NVLink；官方 Megatron 530B 聊天推理示例中 H100 相对 A100 有最高约 30 倍推理吞吐项目标，但是特定模型/集群/网络条件下的厂商投影，不直接代表单卡 Decode 提速。 TensorRT-LLM 在 Llama 2 70B、2048 输入/128 输出示例中，8×H100 DGX 在 Batch 1 约 1.7s 完成整段推理，加大 Batch 可显著提升系统吞吐，说明“单流时延”和“合批吞吐”要分开看。

剩余矛盾：只要 Decode 小 Batch、全精度、权重主要在 HBM，算术强度低就会导致峰值 FLOPS 利用率不高；FP8/INT4、FlashAttention、PagedAttention、连续批处理、投机解码可缓解，但不改变“小 Batch 权重读取量≈模型大小”的物理下限。

## 三、破局“内存墙”的其他方法

### 3.1 数值与算法优化

- **量化**：FP8、INT8、INT4 降低每参数字节数。以 70B 为例，FP16 权重 140GB，INT4 约 35GB；仅按全量读权重估算，H100 3.35TB/s 下理想单步下限由 41.8ms 降至约 10.4ms，但这只是带宽下限，不含KV、内核与通信。
- **稀疏化**：结构化稀疏可与支持稀疏的 Tensor Core 配合降低有效计算/权重量，但推理内核、校准与质量损失要单独评估。
- **投机解码**：小草稿模型先出 k 个候选，目标模型并行验证，用一次大模型前向产出多个 token，提高每次权重读取的有效 token 数；它不是把 GEMV 变 GEMM，但能改善小 Batch 有效吞吐。
- **GQA/MQA、KV 量化、前缀复用**：压缩 KV 体积，降低 Decode Attention 的访存与跨节点传输成本。

### 3.2 近存与存算一体

- **HBM-PIM / 内存内计算**：在 HBM 堆栈或内存侧加入乘加，减少权重从颗粒到计算单元的长距离搬运。
- **CIM/ReRAM 等新兴器件**：适合特定低精度推理研究，但生态、良率、编程模型和大模型商用成熟度仍是要验证项，不宜在产业主线里过度承诺。

### 3.3 空间数据流/确定式架构

核心是用编译器静态排布计算、数据移动与同步，片上 SRAM 作主工作区，减少动态调度、硬件缓存未命中带来的不确定性。后面第四节专述。

## 四、数据流架构的工程挑战

### 4.1 SRAM 容量与成本

先进节点下 SRAM 扩展慢。单芯数百 MB 是现实值：GroqChip 230MB 、Groq3 LPU 500MB 。70B FP16 全量 140GB，显然不能单芯 SRAM 放下；即使 INT4 也有约 35GB。解决方法是多芯层切分、只缓存活跃层、配合HBM/DRAM做溢出。NVIDIA Groq3 LPX 资料中每托盘还有主机侧 DRAM 扩展至最多 256GB、用 fabic 扩展，说明纯 SRAM 不够时仍需分层存储。

成本上，片上 SRAM 占裸片面积大，单位容量比片外 HBM/DRAM 贵得多；是否划算要看目标场景省下的时延与能耗是否能转化为产品价值。

### 4.2 编译器是核心壁垒

数据流把很多 GPU 运行时调度前移到编译器：

- 算子到 PE 的 Placement；
- 数据路由避免死锁与拥塞；
- 周期级排程，使计算、搬运、同步重叠；
- 动态序列长度、MoE 路由、前缀缓存如何重编译或预留可重构区域。

问题不是简单“NP-Hard”四个字，而是：静态编译大模型可能很慢，动态请求可能产气气泡，MoE 专家选择若运行期才确定，就要做预处理绑定、投机路由或混合动态调度。相较之下，CUDA/Triton 对动态 DL 工作负载更成熟，这是数据流芯片商业化最难的部分。

### 4.3 生态与迁移

没有类似 CUDA 的统一生态，客户要改模型导入、调优、监控、回滚。Graphcore 等曾推IPU/数据流类方案但商业承压，说明“架构理论上更优”不等同“可替代GPU生态”。新方案最好走异构：GPU 跑训练/Prefill/高并发，数据流跑特定低时延Decode或子模型。

## 六、系统级异构终局：P/D 解耦与KV传输

### 6.1 Prefill-Decode Disaggregation

思路：Prefill 池用高 FLOPS、大HBM GPU，快速吃长Prompt、建KV；Decode 池用高带宽/近存/确定式芯片，承接KV后逐token出字。DistServe、Splitwise、Mooncake 等论文与系统已验证解耦可改善资源隔离与长尾；NVIDIA Dynamo、vLLM、TensorRT-LLM 等也支持相关解耦/KV传输。

收益：Prefill 不被Decode拖垮，Decode 不被长Prompt突发占用；两池独立扩缩。

### 6.2 KV Cache 传输定量

KV 大小近似：

```text
KV Bytes ≈ 2 × L × S × H × B_head × n_layers
```

更工程化可用每层每token字节数×层数×序列长度。以某27B示例资料为例：4k上下文KV约0.268GB，64k约4.295GB；不同模型因GQA头数、隐藏维、层数差异很大。 70B 资料另有4k约1.3GB的估算，说明不能跨模型套用单一数字。

传输时间下限：

```text
t ≈ KVBytes / Bandwidth
```

- 节点内 NVLink 4.0 约900GB/s、NVLink5约1.8TB/s；
- H100 NVLink 双向900GB/s、PCIe Gen5 单GPU约128GB/s；
- 跨机 200Gbps RDMA 折合约25GB/s理想有效，400Gbps约50GB/s；
- CXL Type-3 共享内存可减RDMA协议栈，但当前设备一致性、原子性与跨节点能力仍受限制。

示例：某27B 4k KV 0.268GB，25GB/s RDMA理想≈10.7ms；64k 4.295GB，25GB/s≈171.8ms，50GB/s≈85.9ms。 若用NVLink 900GB/s，0.268GB≈0.3ms，4.295GB≈4.8ms。结论：短中上下文解耦传输可接受，超长上下文要把“Prefill计算+KV传输+Decode首步”一起算，否则解耦反而增加TTFT。

缓解办法：

- 分层流水传输，Prefill算完一层传一层，与Decode重叠；
- KV量化、GQA、MLA压缩；
- 本地大HBM缓存高频前缀，跨节点只用RDMA/CXL传增量；
- 对MoE/长文本做拓扑感知放置。

## 七、商业落地与生态博弈

- **GPU 通用底座**：训练、高并发推理、长上下文HBM、CUDA/Triton生态短期难替代。H100 的FP8、MIG、NVLink与TensorRT-LLM已形成完整推理栈。
- **数据流利基**：低时延语音、实时Agent、部分端侧控制、可放入SRAM的子模型或对确定性要求极高的金融/安全场景。Groq类芯片用确定式执行和片上SRAM切入，但大模型全量部署依赖多芯与生态。
- **混合路线更现实**：Rubin GPU负责Attention/Prefill、LPU/数据流负责FFN或低时延Decode切分；或用GPU+SRAM加速卡做Attention-FFN分解。NVIDIA Groq3 LPX资料即强调Rubin GPU与LPU协同、编译器管数据移动。
- **历史教训**：单纯“微架构更高能效”不足以战胜软件生态、模型覆盖、客户工具和总拥有成本。商用成功要看编译器自动化、框架插件、故障排查和规模化运维。

## 八、结语

大模型推理的物理本质可概括为：

1. Prefill 看算力与可并行度，HBM容量和FLOPS重要；
2. 小Batch Decode 看“每token搬多少字节、用多大片上/近存带宽搬”；
3. 算法减字节（量化、稀疏、投机、GQA）与架构减搬运（近存、SRAM、PIM、数据流）是同一问题的两层解法；
4. 单架构替代不现实，Prefill-Decode解耦、GPU+数据流/近存加速、高速KV传输的异构系统更可能是终局。

数据流芯片的价值不在“全面打败GPU”，而在把小Batch、低时延、确定式Decode从通用GPU的次优区中独立出来，形成专门硬件层。未来竞争焦点会是编译器、片上/近存层级、跨节点KV传输与软件生态，而不是只比标称TFLOPS。
