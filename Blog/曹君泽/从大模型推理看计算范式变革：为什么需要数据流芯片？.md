# 从大模型推理看计算范式变革：数据流芯片的适用性分析

## 引言：算力需求的结构性转移

过去十余年中，深度学习训练与通用推理主要依赖 SIMT（单指令多线程）架构的 GPU。随着大语言模型（LLM）应用增加，AI 计算重心正在从离线预训练转向在线自回归推理。

在生产环境中，自回归生成（Decode）阶段通常占据用户请求 80% 以上的时间。该阶段的计算特性使系统性能瓶颈不再主要由峰值浮点算力（Peak FLOPS）决定，而是受存储架构的数据搬运能力限制。在低并发和严格交互时延约束下，传统 GPU 面临物理层面的限制，数据流（Dataflow / Spatial Architecture）架构可用于补充 GPU 在特定负载下的不足。

---

## 一、大模型推理的物理诉求与阶段划分

大模型推理不是单一连续的计算过程，而是由两个代数形态不同的阶段构成。

```
                  ┌──────────────────────────────────────────────┐
                  │            大模型推理的两大计算阶段           │
                  └──────────────────────┬───────────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
   【Prefill 阶段: 吞吐优先】                       【Decode 阶段: 延迟优先】
   • 核心算子: 稠密矩阵乘 (Dense GEMM)              • 核心算子: 矩阵乘向量 (GEMV)
   • 算术强度: 较高 (数十~数百 FLOPs/Byte)          • 算术强度: 极低 (仅 1~2 FLOPs/Byte)
   • 物理瓶颈: 浮点算力 (Compute-Bound)             • 物理瓶颈: 显存访存带宽 (Memory-Bound)
   • 核心指标: 首字延迟 (TTFT)                      • 核心指标: 字间生成速度 (TPOT)
```

### 1.1 Prefill 阶段：稠密矩阵乘与计算受限

- **计算范式：** 稠密矩阵乘（Dense GEMM）。用户输入的 Prompt（数十至数千个 Token）被并行展开，输入序列的所有词元在前向传播中同时建立注意力并生成初始 KV Cache。
- **算术强度：** 随输入序列长度 $N$ 增加，通常可达数十至数百 $\text{FLOPs/Byte}$。
- **物理瓶颈：** 处于计算受限（Compute-Bound）区间。增加 Tensor Core 阵列并提高主频，可以降低首字时延（Time to First Token, TTFT）。

### 1.2 Decode 阶段：矩阵乘向量与访存受限

- **计算范式：** 矩阵乘向量（GEMV）。自回归每前进一步只处理最新生成的 1 个 Token，但为了完成各层线性投影与前馈计算，系统必须将整个模型的全部权重从显存中读取一遍。
- **算术强度下降：** 以 FP16 精度为例，每个参数占 2 字节，一次前向计算约消耗 2 次浮点操作，权重侧的理论算术强度约为：

$$
I \approx \frac{2 \times P \text{ FLOPs}}{2 \times P \text{ Bytes}} = 1 \text{ FLOP/Byte}
$$

- **物理瓶颈：** 硬件处于访存受限（Memory-Bound）状态。决定每秒吐字速度（Time Per Output Token, TPOT）的核心瓶颈与算力上限关系不大，主要取决于内存物理接口将权重送达计算单元的速率。

### 1.3 Roofline 视角下的物理差距

以配备 80GB HBM3、内存带宽 3.35 TB/s、Dense FP16 算力约 989 TFLOPS 的 NVIDIA H100 SXM 为例：

- 计算与访存的饱和平衡拐点（Roofline Knee Point）为：

$$
I^* = \frac{989 \times 10^{12} \text{ FLOPs/s}}{3.35 \times 10^{12} \text{ Bytes/s}} \approx 295 \text{ FLOP/Byte}
$$

- 在 Batch=1 的 Decode 阶段，实际算术强度约为 $1 \text{ FLOP/Byte}$，远低于 295 的饱和点。因此在单流自回归场景下，GPU 的大部分计算单元无法被充分利用。

### 1.4 下一代 AI 应用对低 Batch 单流时延的约束

在实际业务场景中，通过无限制增加 Batch 来提高吞吐并不适用于所有情况：

1. **端侧与个人设备：** 智能座舱、AI PC、机器人等场景通常面向单一物理用户，请求常为 Batch=1，无法通过多用户并发分摊权重读取开销。
2. **实时全双工交互：** 人类对对话停顿的感知极限通常在 200~300ms。扣除 ASR 语音识别、TTS 语音合成与网络 RTT，留给 LLM 的单步思考与吐字时间预算只有数十毫秒。
3. **深度思考链 Agent：** 复杂逻辑推理模型需要在后台生成数千个中间 Token。如果单流生成速度停留在 30~40 Tokens/s，用户等待时间将以分钟计；单流吐字需提升到 300~800+ Tokens/s，才能支持思考链的实时交付。

## 二、传统 GPU 在低 Batch Decode 下的架构限制

现代 GPU 建立在 SIMT 与分层存储体系之上。该微架构在面对低 Batch 自回归时，存在三项结构性矛盾：

### 2.1 延迟掩盖机制在低并发下失效

GPU 的设计方式是通过大量线程并发（Thread-Level Parallelism）掩盖片外访存延迟：当 Warp 0 发起 HBM 读取并被挂起时，硬件调度器切换至 Warp 1、Warp 2 继续计算。

但在 Batch=1 场景下，可用的活跃 Warp 数量大幅减少。缺少足够的计算线程填补 HBM 访存时延，大量算术逻辑单元只能等待。

### 2.2 实际吞吐受 HBM 物理带宽限制

以单卡可完整容纳的 LLaMA-3-8B（FP16 权重约 16GB）为例，在配备 3.35 TB/s 带宽的 H100 上执行 Batch=1 Decode：

- 仅全量读取一次模型权重，物理传输时间的下限为：

$$
t_{\text{weight}} \ge \frac{16 \text{ GB}}{3350 \text{ GB/s}} \approx 4.78 \text{ ms/Token}
$$

- 对应的单流生成理论上限约为 209 Tokens/s。若计入 KV Cache 读写、Attention 计算、片内总线延迟及驱动调度，实际测试通常在 100~150 Tokens/s 左右。
- 此时，GPU 的模型实际算力利用率（MFU）通常降至 10%~20%。用户购置的浮点算力中，较大比例的硅片面积用于内存搬运。

### 2.3 通用处理器的控制开销与能效问题

通用处理器为了维持可编程性，需要承担较高的控制面开销：

- **控制面晶体管消耗：** 指令提取（Fetch）、指令译码（Decode）、分支预测、乱序调度与 Warp 仲裁电路持续消耗动态功耗。
- **数据搬运能量差异：** 在先进半导体工艺下，一次 16-bit 浮点 MAC 计算消耗能量约为 0.1~0.5 pJ，而将数据通过长距离硅中介层与高频 SerDes 从片外 HBM 搬运到核心，能耗可达 100~200 pJ。
- 在小算术强度下，GPU 较多电能消耗在指令管理与长距离走线的电荷充放上，导致单 Token 能耗较高。

## 三、数据流芯片的微架构：空间计算如何应对访存瓶颈

与 GPU 的时间复用（Temporal）不同，数据流芯片采用空间计算（Spatial Computing）的微架构设计范式。代表方案包括 Groq LPU、Cerebras 等。

```
传统 GPU (时间复用):
[计算工位 (SM)] ──第 1 拍: 算 QKV ──► [写回显存/中间缓存]
                ──第 2 拍: 算 Softmax ◄── [从显存/缓存拉回]
                ──第 3 拍: 算 FFN ──► [再次写回]

数据流架构 (空间平铺流水线):
[输入数据] ──► [PE 0: 算 QKV] ──(片内微米级短线)──► [PE 1: 算 Softmax] ──(片内短线)──► [PE 2: 算 FFN] ──► [输出]
              (计算单元固定角色，数据流经芯片，无中间落盘)
```

### 3.1 空间流水线替代时间复用：减少中间激活回写

在数据流芯片中，算子图被物理平铺在二维处理单元（PE）阵列上。

- **波前流动：** 输入张量流经物理阵列。PE0 计算完成后，可通过片上微米级相邻金属走线将结果注入下游 PE1。中间激活值驻留在本地 FIFO 或局部 Scratchpad 中，减少反复向外部大内存回写中间结果的开销。

### 3.2 片上分布式 SRAM：降低访存差距

数据流芯片通常不采用片外 HBM，而是在芯片表面集成数百 MB 至数 GB 的分布式片上 SRAM：

- 片上 SRAM 直连计算阵列，可提供数十至数百 TB/s 的片上总互联带宽。例如 Groq 第一代芯片提供 80 TB/s 片上带宽，可将访存带宽提升 1~2 个数量级。
- 物理距离被压缩在微米级别，数据读取能耗从 HBM 的数百 pJ 降至几 pJ，从物理层面缓解“内存墙”。

### 3.3 周期确定性：减少长尾抖动

静态数据流芯片（以 Groq TSP/LPU 为典型）将调度权从芯片内部上移至编译器：

- **无硬件动态仲裁：** 芯片内部没有 Warp 调度器、动态分支预测和硬件缓存一致性维护。
- **编译器时钟级排程：** 编译器在离线编译时规划每个数据包在第几个时钟周期流向哪个 PE 坐标。
- **低抖动交付：** 硬件执行时没有冲突、死锁和 Cache Miss 重试。在运行稳定的自回归任务时，P99 尾部延迟与 P50 中位数延迟之比可接近 1.0。

## 四、核心架构与运行特征对比

| 评估维度 | 传统通用 GPU 集群 | 专用空间数据流芯片 | 物理实质 |
| --- | --- | --- | --- |
| **计算范式** | 时间复用（Temporal）：指令驱动，多线程并发 | 空间计算（Spatial）：数据流驱动，流水线空间平铺 | GPU 轮流使用算术核心；数据流以固定管线流动加工。 |
| **主存架构** | 大容量片外 HBM（数十至数百 GB），总线带宽 3~8 TB/s | 大面积片内分布式 SRAM（数百 MB/芯），片上聚合带宽 80~150+ TB/s | 用片内近存减少片外引脚延迟。 |
| **算力利用率（MFU @ BS=1）** | 5%~15% | 45%~65%+ | 数据流减少显存停顿等待。 |
| **单流时延（Batch=1 Decode）** | 受限于 HBM 搬运下限，8B 模型约 100~150 Tokens/s | 8B 模型可达 500~800+ Tokens/s | 片上高带宽减少权重搬运等待。 |
| **时延抖动比（P99 / P50）** | 1.3~1.8 | 约 1.00~1.05 | 静态编译编排减少运行期硬件仲裁。 |
| **单 Token 净能耗** | 较高，较多电能耗于 SerDes 与空转 | 显著降低，降至 1/3~1/5 | 片内微米级金属走线降低高电容充放电功耗。 |
| **编译器开发难度** | 成熟，CUDA / Triton / JIT 生态完善 | 极高，NP-Hard 空间映射与寻路 | 调度复杂度从芯片内部转移至离线编译器。 |

## 五、数据流架构的代价与工程限制

数据流芯片在获得低单流延迟与确定性的同时，也承担了较严格的工程代价：

### 5.1 SRAM 容量限制与集群堆叠成本（CapEx）

在先进半导体工艺节点（如 4nm/3nm）下，SRAM 晶体管微缩已接近停滞。单颗芯片能集成的 SRAM 容量上限通常只有几百 MB。

- 单颗数据流芯片无法装下几十 GB 甚至几百 GB 的大模型全量权重。
- **集群门槛较高：** 运行全尺寸 70B 模型，必须使用数十甚至上百颗芯片，通过高速片间互联网络（C2C Cables）组成分布式 SRAM 池。整机系统的初始采购硬件成本与互联拓扑复杂度显著增加。

### 5.2 编译器是主要技术壁垒

数据流芯片的性能在很大程度上依赖编译器：

- 编译器必须在一张较大的硬件物理网格上，同时解决模型计算图的空间切片（Tiling）、算子放置（Placement）、无拥塞寻路（Routing）与时钟周期排程（Scheduling），这属于高维 NP-Hard 组合优化问题。
- 面对包含动态上下文长度、稀疏激活条件分支以及 MoE（混合专家模型）动态路由的复杂任务，纯静态编排容易产生流水线空泡（Stall Bubbles），对编译系统的动态适应性提出较高要求。

## 六、趋势：Prefill 与 Decode 走向物理解耦

体系结构演进表明，较少存在能够覆盖所有工作负载的“完美芯片”。未来的大模型计算基础设施，可能走向 Prefill 与 Decode 物理分离的异构解耦系统。

```
                               【数据中心 P/D 解耦异构系统拓扑】

            ┌────────────────────────────────────────────────────────┐
            │                  用户/业务请求进入 (Prompt)             │
            └───────────────────────────┬────────────────────────────┘
                                        │
                                        ▼
    ┌────────────────────────────────────────────────────────────────────────┐
    │ 1. Prefill 算力节点: GPU 的主要适用场景 (Dense GEMM / Compute-Bound)   │
    │    • 硬件形态: 搭载大容量 HBM 的通用 GPU 节点                          │
    │    • 核心任务: 处理长 Prompt，利用 TFLOPS 算力，生成 KV Cache           │
    └───────────────────────────────────┬────────────────────────────────────┘
                                        │
                                        │ 流式交付 KV Cache
                                        │ (走 PCIe P2P / CXL Fabric / RoCE 网络)
                                        ▼
    ┌────────────────────────────────────────────────────────────────────────┐
    │ 2. Decode 算力节点: 数据流芯片的适用场景 (GEMV / Memory-Bound)          │
    │    • 硬件形态: 分布式大 SRAM / 空间流式流水线专用芯片/卡                │
    │    • 核心任务: 承接初始 KV Cache，以较高单字速率与较低能耗逐字生成回复   │
    │    • 运行特征: 较低 TPOT、较低能耗、低抖动实时交付                      │
    └───────────────────────────────────┬────────────────────────────────────┘
                                        │
                                        ▼
            ┌────────────────────────────────────────────────────────┐
            │                   低时延流式响应返回用户                │
            └────────────────────────────────────────────────────────┘
```

1. **Prefill 计算池（GPU 适用）：** 利用其在稠密计算与大容量 HBM 上的积累，并行处理长文本 Prompt，降低 TTFT；
2. **中间状态流式交付：** 初始计算完成后的 KV Cache 通过高速总线（如 PCIe P2P、CXL 共享内存或专用 RDMA 网络）跨节点推送给 Decode 节点；
3. **Decode 计算池（数据流芯片适用）：** 接收到初始状态后，专用数据流加速节点依靠片上高带宽 SRAM 和空间流水线，以较高频率自回归吐字，提供低抖动、低时延的生成体验。

## 结语

大模型推理的底层算力矛盾，本质上是自回归生成极低的算术强度与通用芯片访存供给之间的物理冲突。

数据流芯片不是对通用 GPU 生态的全面否定，而是针对小 Batch、低时延自回归任务的架构优化方向。它通过空间计算替代时间复用，用片上高带宽降低访存瓶颈，用编译期确定性减少运行期控制能耗。理解这种微架构与物理约束之间的权衡，有助于在大模型落地过程中，构建具备成本效益与低时延体验的下一代 AI 算力基础设施。
