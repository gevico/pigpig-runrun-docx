# 契约驱动的独立 RTL 细化与在线联仿自验证闭环（BC 路线研究报告）

> **报告定位**：本文作为 `report.md` 的核心技术专题报告，系统阐述 **契约驱动的独立 RTL 细化与证据化自验证闭环（BC 路线）** 的宏观架构、五层硬件 Spec 设计、AI Agent 受控转化机制、gem5 在线联仿方案、实证成果及后续演进方向。全文面向团队汇报与技术评审，聚焦**最终落地方案、关键量化结果与清晰的工程边界**。

---

## 1. 战略背景：从“源码直译”转向“Spec 驱动的独立 RTL 与闭环自验证”

在探索将既有 gem5 微架构模型推进到物理 RTL 的过程中，早期实验暴露出一个根本矛盾：**gem5 的核心价值在于高速全系统架构探索，而物理 RTL 的核心要求是周期精确、静态定宽与确定性反压**。试图强行把已有的行为级 gem5 C++ 代码直译或通过宏切换变为 RTL，不仅会破坏既有 gem5 模型的简洁性与仿真速度，还会遭遇状态提交时刻、端口并行度、流控反压和同拍仲裁等不可调和的语义分歧。

因此，针对 GW100 中**已经成型并稳定运行的既有 gem5 模块**，我们将研究目标正式重新定义为：

> **面向既有 gem5 微架构模型的契约驱动 RTL 细化与证据化验证（Contract-Guided RTL Refinement and Evidence-Driven Verification）**——不再要求 gem5 代码与 RTL 代码“长得一样”，而是以**独立冻结的五层硬件 Spec（Hardware Contract）**为核心枢纽，把“Spec 指导 RTL 生成 → 离线双层差分自验证 → 在线回接 gem5 系统级联仿”打通为一条确定性、可审计的工程流水线，从而安全引入 AI Agent 承担 RTL 实现与局部修复。

---

## 2. 宏观闭环架构：Spec → RTL → 回接 gem5 的自验证飞轮

BC 路线的本质是用**确定性的规格、门禁与仿真裁判**，把概率性的 Agent 生成与人工迭代约束在可控边界内。整条闭环由四大相互独立的工程实体组成：

```text
               ==========================================
               ||    五层冻结硬件 Spec (Hardware Contract)  ||
               ||  Interface · Functional · Concurrency   ||
               ||        Timing · Reset & Error           ||
               ==========================================
                      /                          \
                     v                            v
       [A. 冻结参考基线]                   [B. 独立 RTL 候选]
     上游 gem5 C++ 模型                 独立编写 / Agent 生成的 SV
    （零修改，受权限保护）               （Agent 唯一可编辑区域）
                     |                            |
                     +-------------+--------------+
                                   v
             ==============================================
             ||   [C. 离线双层差分验证与证据修复基础设施]    ||
             ||  1. 静态契约门禁 + Verilator Lint          ||
             ||  2. Level 1 事务级黄金对拍 + 单调回归锁     ||
             ||  3. Level 2 周期级协议/可见性/反压检查器    ||
             ||  4. 首分歧定位 -> 无状态修复证据包 -> Agent ||
             ==============================================
                                   |
                                   v  (通过全部离线门禁后)
             ==============================================
             ||   [D. 在线回接 gem5 全系统联仿 (C 阶段)]    ||
             ||  薄适配壳 (RTL Adapter) 封装 Verilator RTL ||
             ||  无缝接入原有 gem5 接口与 TimingPort Retry  ||
             ||  Mode 0 (原 C++) vs Mode 1 (RTL) A/B 验收   ||
             ==============================================
```

### 面向 AI Agent 的权限隔离与自验证机制

为了让 Agent 在硬件开发中真正做到“**可控转化 + 成果自验证**”而非产生不可信的“幻觉代码”，本闭环制定了三项硬规则：

1. **物理级权限隔离（杜绝 Reference Drift）**：
   - **只读保护区**：上游 gem5 参考实现、五层冻结 Spec、记分板与历史回归锁基线——严禁 Agent 为凑通过测试而私自修改参考标准或删减历史用例。
   - **受控可写区**：仅限候选 RTL 文件；Agent 提交的任何修改必须自动经过静态门禁与双层仿真裁判。
2. **无状态证据驱动修复（Stateless Evidence-Driven Repair）**：
   - 相比把冗长报错日志与多轮对话历史全量灌给大模型，验证引擎在捕获**首次分歧**后立即截停，确定性抽取最小诊断包（冻结 Spec 引用 + 首个失败事务编号与 RTL 周期 + 期望/实际信号差异 + 最近一次复位至出错点的复现切片）。
   - Agent 仅基于该精简证据包执行无状态局部修复，大幅压缩上下文噪声并提高收敛确定性。
3. **单调递增回归锁（Monotonic Regression Lock）**：
   - 每捕获并修复一类缺陷，对应的失败复现切片即被永久追加至回归锁集合；后续任何新版本 RTL 必须全量通过历史回归锁，从机制上消灭“修好新 Bug 破坏旧功能”的退化循环。

## 3. 五层硬件 Spec 设计：把模糊分歧转化为可验证裁决

前期研究发现，仅记录端口名与位宽的接口文件远远不足以约束真实硬件——**高层事务结果相同，并不意味着两个模型在所有可观察时间点上等价**（这一观点与 [Bombieri et al. (MEMOCODE 2007)](https://eprints.soton.ac.uk/263822/1/jpms-memocode07.pdf) 关于 TLM/RTL 事件级等价性的经典研究一致）。

为此，BC 路线将硬件 Spec 正式结构化为**五层机器可读契约**，并将 gem5 与 RTL 之间最易引发扯皮的四类语义分歧在设计之初就做出明确裁决（以 GW100 `CtSync` 为锚点示范）：

| Spec 层次 | 核心定义内容 | 对 GW100 `CtSync` 的正式裁决示例 |
|---|---|---|
| **1. Interface（接口层）** | 模块名、全部端口方向与精确位宽、地址映射窗口、状态编码及禁用非可综合语法 | 21 个冻结端口、64 位地址经 mod 16 MiB 归一化至 `[0x80_0000, 0x80_0080)`、状态码 `Ok=0 / Reject=1 / Fault=2`，严禁 `initial`/`#delay`/`$random` |
| **2. Functional（功能层）** | 内部状态位宽、合法读写语义与边界算术行为 | 32×32 位无符号计数器；32 位加法溢出时必须返回 `Reject` 且**严格保持原值不变**；`tryWait` 仅在计数值足够时消费 |
| **3. Concurrency（并发与仲裁层）** | 物理端口并行度、多发起方同拍碰撞的线性化规则与读写优先级 | **单端口 MMIO**（每拍至多 1 笔，原 gem5 逐计数器排队明确登记为软件调度抽象）；同拍 MMIO 写与 `tryWait` 严格执行 **读旧值无旁路（Read-Old, No Bypass）**；同拍 MMIO 写与 `local_sig` 按确定性优先级原子累加 |
| **4. Timing（时序与流控层）** | 输入采样时刻、状态提交边沿、外部可见周期与反压流控规则 | **同步上升沿提交、下一周期可见**（拒绝复制 gem5 瞬时改值的时间穿越）；单槽响应 Skid 反压（下游阻塞时 `mmio_req_ready` 物理拉低，保持响应稳定零丢包） |
| **5. Reset & Error（复位与异常层）** | 复位有效电平、同拍复位优先级与错误事务零副作用不变量 | 异步低有效复位覆盖同拍一切读写操作；任何越界、非对齐、空指针或溢出拒绝事务严禁产生任何状态副作用 |

### 双层差分验证架构（Level 1 + Level 2）
基于五层 Spec，验证体系不再混为一谈，而是清晰划分为两层：
- **Level 1（事务级等价性）**：对照冻结的 gem5 参考模型，校验每笔事务的接收状态、返回数据、溢出处理与状态副作用是否一致，允许 Spec 明确文档化的延迟差异。
- **Level 2（周期级等价性）**：对照 Spec 的时序与并发层，逐拍检查 `valid/ready` 握手、上升沿提交可见性、多拍反压稳态、复位优先以及同拍读写仲裁，补齐事务级对拍无法触达的微架构盲区。

## 4. C 阶段回接 gem5：从离线验证走向全系统在线联仿

离线 Trace 对拍只能证明模块在既定激励下符合 Spec；要真正验证 RTL 能否替换进真实芯片模拟器，必须通过 C 阶段完成**在线联仿回环**（参考 [gem5+rtl (ICPP 2021)](https://upcommons.upc.edu/bitstream/handle/2117/354158/icpp21.pdf) 与 [gem5 Memory System](https://www.gem5.org/documentation/general_docs/memory_system/) 的流控机制）：

- **零入侵接口封装**：保持上游 `CtWindowHandler` 对外接口不变，新增薄适配壳 `CtSyncRtlAdapter` 内部驱动 Verilator 编译生成的 RTL 模型。所有 gem5 概念（`Tick`、`CtClockIf`、`CtAccess`、单端口排队时刻）严格隔离在适配壳内，RTL 源码保持 100% 纯净。
- **反压协议对齐**：RTL 侧的 `mmio_req_ready == 0` 在适配层映射为非阻塞准入信号，直接对接 gem5 `TimingPort` 的标准流控语义——请求被拒时 `recvTimingReq()` 返回 `false` 并置位挂起标志，待下游响应通道释放、RTL `mmio_req_ready` 恢复拉高后，由适配层触发 `sendRetryReq()` 重试，实现零丢包、零重复的系统级反压透传。
- **A/B 双模式系统验证**：在同一套上层 Compute Tile 硬件模块与工作负载下，并排运行 **Mode 0（原版 C++ 模型）** 与 **Mode 1（Verilator RTL 适配壳）**，对 Spec 规定的功能不变量要求 100% 比特一致，对 Spec 允许的物理单端口时序差异做显式量化比对。

## 5. 关键实证成果（以 GW100 `CtSync` 及全 9 模块 Compute Tile 为例）

在零修改上游 `gem5-ext/` 源码的前提下，整条 BC 闭环已在 `CtSync` 与全 9 模块 Compute Tile 上完成了端到端实测验证：

| 验证环节 | 测试场景与覆盖规模 | 实测结果 |
|---|---|---|
| **1. 静态契约门禁（防 Agent 漂移）** | 构造接口漂移反例（缺失 `mmio_req_ready`、地址缩窄为 32 位、混入 `initial`/`$display`） | 在仿真前即确定性拦截全部 **5 项违规**，阻止非法 RTL 进入仿真 |
| **2. 缺陷定位 + 无状态修复包 + 回归上锁** | 构造隐蔽功能 Bug 反例（通过静态门禁，但 32 位加法溢出回绕而非拒绝） | 在 **第 26 笔事务 / 第 40 周期** 精准截停并报出期望 `status=1` vs 实测 `status=0`；自动生成精简无状态修复证据包，并将自最近一次复位起的 **10 笔复现切片** 永久锁入回归集 |
| **3. Level 1 事务级全量对拍** | 修复版 RTL 回放上游原版 `ct_sync.cc` 录制的 **230 笔黄金事务**（30 笔定向边界 + 200 笔随机压力）及 10 笔回归锁 | **230/230** 黄金事务（跨 357 个 RTL 周期）+ **10/10** 回归锁（跨 20 个 RTL 周期）**100% 比特级一致**；通过 `Verilator --lint-only -Wall` 0 警告 |
| **4. Level 2 周期级协议与反压矩阵** | 覆盖全部 32 计数器溢出零副作用、同步上升沿可见性、同拍写+等原子保留（`3+4-3=4`）、同拍写+signal 累加（`10+20=30`）、复位优先、4 拍连续停顿、以及 **64 笔满载突发 + ~33% 随机反压** | **7/7 周期级套件全部通过**（64 笔随机反压突发共 92 周期，累计和 `2080` 精确无误，零丢包/零重复） |
| **5. C 阶段在线 A/B 与全 9 模块 Compute Tile 联仿** | 将 Verilator RTL 无缝接入全部 7 个未修改上游 Compute Tile 模块（`CtSram`、`CtWindow`、`CtCtrlSram`、`CtNidma`、`CtMatrix`、`CtVector`、`CtCtrl`），运行端到端张量计算流水线与 `TimingPort` Retry 原型 | - 单模块三发起方流水线 **96 笔事务 + 全 32 计数器终态 100% 一致**（292 周期）；<br>- 全 9 模块端到端流水线（`Nidma → Matmul → Sync → Vector → Nidma`）Mode 0 与 Mode 1 均在 4 步内输出完全一致的 `[121, 256]`，8 轮串联计算链 16 个浮点输出全匹配；<br>- `TimingPort` Retry 实测在响应阻塞时准确触发 `recvTimingReq()==false` 与 `sendRetryReq()` 重发，最终 `sync[4]=35` 零丢包 |

**正式合入完整 `gem5.opt` 整机评估**：经源码审查，将 C 阶段适配器正式合入上游 `Gw100Ct` 仅需 **3 处极小且无架构阻塞的改动**——抽出约 5 行 `CtSyncIf` 抽象接口供 `CtMatrix`/`CtVector` 运行期切换 Mode 0/1；在 `CtPioPort::recvTimingReq` 中补齐约 15 行 `sendRetryReq()` 反压分支；在 `SConscript` 中增加可选条件开关链接 Verilator 静态库。

## 6. 诚实边界与后续演进路线

**总体结论：BC 路线（五层冻结 Spec → 独立 RTL 与双层自验证 → 在线回接 gem5 联仿）在工程上完全可行，已验证了从架构模型到可信 RTL 的完整验证底座，适合作为 GW100 既有复杂模块的长期主线。**

为保持严谨的工程评估，以下四项能力属于**当前尚未完成、下一阶段重点攻克**的范围：

1. **真实硬件综合与物理 PPA 闭环**：当前 `Verilator --lint-only -Wall` 仅验证 Lint/Elaborate 与仿真正确性，不能等同于硬件综合。下一步接入开源 [Yosys](https://yosyshq.readthedocs.io/projects/yosys/en/latest/using_yosys/synthesis/synth.html) 跑通门级逻辑综合，并在统一工艺库与时序约束下接入 [OpenROAD](https://openroad-flow-scripts.readthedocs.io/en/latest/tutorials/FlowTutorial.html) 建立独立的面积、关键路径与功耗基线门禁。
2. **完整 `gem5.opt` 裸机固件全系统 A/B 回归**：在合入上述 3 处极小上游接口改动后，将 Verilator RTL 挂入完整 gem5 仿真器，在真实 RISC-V 裸机固件负载下跑通 Mode 0 / Mode 1 全系统验收。
3. **向异步乱序复杂模块演进（`CtNidma` 记分板升级）**：当前顺序事务对拍器适用于 `CtSync` 这类单事务有序模块；向多拍 FSM、多 Bank SRAM 冲突、多 Outstanding Tag 乱序返回的 `CtNidma` 扩展时，将把对拍器升级为基于协议偏序关系的 **Transaction Scoreboard**，按“单请求 → 多在途 → 乱序回包 → SRAM 冲突 → 完整 NoC”分阶段验证。
4. **受控 AI Agent 消融实验**：目前已完成的是“证据驱动修复基础设施（Evidence-Driven Repair Infrastructure）”。下一步将在稳定验证底座上开展四组对照实验（纯人工 vs. 无约束 Agent vs. Agent + 静态契约门禁 vs. Agent + 完整双层对拍与回归锁），量化评估 Agent 在首次通过率、多轮修复收敛率、历史回归零退化率以及人工介入耗时上的真实工程收益。
