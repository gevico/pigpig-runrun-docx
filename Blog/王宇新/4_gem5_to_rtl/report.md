# 从 gem5 到 rtl

## 引言（Introduction）

本文旨在调研并探讨从 gem5 体系结构模拟器向可综合 RTL 演进的可行性、核心障碍与工程落地路线。

在计算机体系结构与电子设计自动化（EDA）领域，“软件模拟硬件”与“软件综合硬件”长期以来是两条相对独立的技术脉络。前者侧重在通用处理器上高效复现硬件的并发性、反应性与宏观行为（如 QEMU、gem5），后者则致力于将高层程序语言编译、调度并映射为满足面积、功耗与时序（PPA）约束的物理电路（如早期的类 C 综合工具与现代 SystemC/HLS 流程）。两条路线各自都已沉淀出高度成熟的开源生态与工业工具。

本文试图回答一个跨界的核心问题：如何在保留 gem5 全系统架构模拟优势的前提下，打通向底层 RTL 演进的敏捷开发通路——即在完成宏观功能与性能探索后，以可控的工程代价迅速下沉至物理 RTL 以评估真实的硬件行为与电路代价；并进一步跳出单一的“代码语法转换”视角，探讨在 AI Agent 介入的新范式下，如何构建一套结构稳定、可重复验证的硬件敏捷开发流程。

## 1. 从 C 语言到实际电路：确立软硬件鸿沟标尺


在现代 RTL 语言与高层次综合（HLS）成熟之前，学术界和工业界曾持续探索直接以 C 语言作为硬件描述语言（HDL）的可能性，其核心动机在于软件工程师的语言熟悉度以及软硬件协同设计的迁移便利性。然而，大量实践表明，未经修改的标准 C（Vanilla C）在语义根基上与物理电路格格不入。

C 语言诞生于 20 世纪 70 年代资源受限的 PDP-11 机器环境，，本质上是贴近传统通用处理器指令集的冯·诺依曼抽象工具。软件遵循源自图灵机的顺序执行模型，并将内存视为一块平坦、无差别的全局字节数组；而物理硬件天生是空间并行、由外部信号持续驱动并实时响应的反应式系统（Reactive System）。Stephen A. Edwards 在 2006 年的经典综述中系统归纳了类 C 语言向硬件综合时面临的五大核心抽象鸿沟[在 essay/c_to_ctl/从 c 到硬件抽象的总结]：

1. 挑战维度	软硬件底层逻辑冲突	早期类 C 项目的典型弥合尝试
并发模型	软件默认顺序执行，依赖编译器自动提取并行性（如 ILP、流水线）存在上限；硬件依赖显式的空间并行算法。	Cones 将整个 C 函数展平为单拍组合逻辑；HardwareC 通过显式 < > 块声明并行语句；Handel-C 与 Bach C 引入显式并行块；CASH 尝试提取 ILP 生成异步数据流电路。
2. 时序指定	C 语言仅保证逻辑因果序而对“耗时多少周期”保持沉默；硬件中“何时发生”与“发生什么”同等重要。	Transmogrifier C（每次循环/调用占 1 拍）与 Handel-C（每条赋值占 1 拍）采用固定隐式规则；Olympus/HardwareC 与 C2Verilog 引入周期/资源约束由编译器调度；SpecC 通过 wait(clk) 显式划分状态机周期。
数据类型	C 基本类型以字节为单位存储在内存中；硬件基本单元是沿着无状态导线传输的单比特与任意位宽向量。	Transmogrifier C 通过 #pragma、C2Verilog 通过外部 GUI 指定整数位宽；HardwareC、Handel-C 与 BDL 直接向语言新增位向量或显式位宽整数类型。
3. 通信模式	C 依赖平坦全局内存与运行时计算的指针，指针别名（Aliasing）在理论上不可判定；硬件需要延迟可预测的隔离小存储器与静态布线。	BDL 禁用指针与动态内存；C2Verilog 与 Séméria 等人的工作尝试用静态指针分析拆分存储区；HardwareC 与 Handel-C 引入阻塞式会合（Rendezvous）消息通道替代共享内存。
提示与约束	软件中单一运算（如加法）对应固定机器指令；硬件中同一运算对应行波进位、超前进位等多种 PPA 权衡实现。	通过内联 #pragma、语言级约束属性（HardwareC、Bach C、BDL）或外部 GUI/数据库（SpecC）向综合器传递设计意图。



纵观上述早期探索：单纯依靠给 C 语言“打语法补丁”无法从根本上弥合软硬件鸿沟。诸如 Handel-C、BDL、SpecC（新增 33 个关键字）等相对成熟的类 C 硬件语言，在语义上已与标准 C 相去甚远，仅仅借用了 C 的表层语法。更棘手的是，这类语法扩展（Syntax Extension）方案迫使开发者从零维护独立的编译器、仿真器与调试工具链，难以融入主流软件工程生态。


## 2. 从 C++ 到实际电路：类库桥梁与规则路线的天花板

鉴于纯 C 语法扩展路线的生态孤岛困境，业界逐步转向具备面向对象与元编程能力的 C++。从 C++ 迈向硬件建模与电路综合，历史上分化出了两条本质不同的技术路径：

1. 行为仿真与可综合子集路线（类库法）：通过 C++ 类库封装硬件语义，C++ 程序的运行过程即为硬件行为仿真，再由综合工具静态分析其中的可综合子集生成电路；
2. 结构构造路线（元编程/生成器法）：不静态解析 C++ 源码行为，而是直接运行 C++ 程序，在内存中动态构建表示数据通路与有限状态机（FSM）的网表（Netlist）数据结构，再导出为 Verilog 交由传统综合工具处理。

2.1 类库路线：从 Scenic 到 SystemC 的反应式建模

硬件系统天然具备层次化、模块化与明晰的接口边界，这与面向对象编程中的“类”高度契合——这也是 gem5 采用 C++、乃至 QEMU 在 C 语言中自建类对象系统的根本原因。相较于语法扩展，采用类库（Class Libraries）对 SoC 硬件建模的核心优势在于：无需修改语言文法与编译器前端，即可直接复用 GCC/Clang、调试器及成熟软件生态；同时利用类封装物理边界、利用模板支持任意位宽与定点数类型（如 sc_uint<N>）、利用引用机制建模端口互连，并在统一语言框架下支持从系统级、架构级到 RT 级的逐步细化（Refinement）（用 cpp 进行系统设计一文描述了使用 cpp 描述硬件的上层抽象思路）。

作为 SystemC 的重要先驱，Scenic（scenic 一文）清晰地展示了 C++ 类库如何在软件运行时中高效模拟硬件底层的反应性（Reactivity）：

⚬ 并发与混合调度机制：Scenic 将硬件进程封装为继承自基类 sc_process 的对象，底层借助非抢占式协程库承载进程并发，并通过延迟信号赋值（write() 将更新提交至时钟动作列表，在周期末尾统一生效）消除串行仿真中的读写竞争。针对纯线程/协程在每拍轮询条件时引发的严重上下文切换瓶颈，Scenic 提出混合仿真方案与延迟求值表达式（Lambda 对象）（包括静态函数闭包与基于运算符重载的动态表达式树），将挂起进程的等待条件暴露给时钟调度器统一求值，仅在条件成立时唤醒对应进程，显著降低了上下文切换开销。
⚬ 正交抢占建模：硬件中复位（Reset）、断电（Power-down）等全局抢占信号在传统 HDL 中需在每个时钟周期显式轮询，代码极其冗长。Scenic 通过在构造函数中注册监视列表（watching()），并在时钟边沿条件触发时抛出 sc_user 异常，巧妙借助 C++ 的 try/catch 异常处理机制，以与其他控制流完全正交的方式实现了多优先级硬件抢占。
⚬ 结构与类型封装：通过模板提供信号与多值逻辑类型（std_ulogic），通过对信号的 C++ 引用（Reference）在构造函数初始化列表中完成端口绑定，并利用优先队列支持多非同频时钟（Non-isochronous Clocks）的异步调度。

2.2 结构构造路线：以 Ocapi 为代表的生成器范式

与 Scenic/SystemC 截然不同，比利时 IMEC 开发的 Ocapi 系统（Schaumont 等人，DAC 1998，见 [1] 中综述）同样基于 C++，却采取了声明式的结构构造思路。开发者编写的 C++ 程序运行的目的不是模拟每个时钟周期的行为，而是构造数据通路、导线、总线与显式有限状态机（FSM）的内存图结构，随后直接输出为 Verilog。在这种范式下，C++ 的数组、指针和循环仅作为构造期（Elaboration）的辅助手段，从而绕开了传统综合器对运行期指针与控制流的复杂分析难题。这一思想在后来演进为 Chisel、PyMTL3 等现代嵌入式硬件构造语言（HCL）的先声。

2.3 规则驱动路线的现代演进与核心局限

2006 年之后，以 AutoPilot（后演进为 Xilinx Vivado/Vitis HLS）、Catapult C、Stratus HLS 与 LegUp 为代表的现代 C/C++ HLS 工具，借助 SSA 中间表示、差分约束调度与阵列分区等编译优化技术，在规则数据流密集型内核（如矩阵乘、卷积、DSP 算子）上取得了巨大成功，部分缓解了 Edwards 对综合性能的担忧。

然而，在面对控制密集型、动态事件驱动、多模块异步交互的复杂体系结构模型（如片上互连、复杂仲裁器、乱序微架构以及全系统模拟器）时并发、时序与内存模型鸿沟依然牢固存在。更深层的矛盾在于，C++ 类库路线在长期发展中形成了“仿真子集”与“综合子集”的严重割裂：为了追求高层架构探索的速度与表达力，体系结构模型大量采用高级 C++ 特性、动态容器与抽象通信协议；而一旦进入可综合流程（如 SystemC RTL 子集），设计者又被迫退回到近似 Verilog 的繁琐显式状态机描述。这表明，在传统规则驱动范式下，高层次架构模拟的“敏捷性”与物理电路综合的“确定性”之间仍存在难以自动跨越的断层。

## 3. gem5 的能力边界与分层解耦基线

既然 SystemC 已在电子系统级（ESL）设计与综合领域得到广泛应用，我们为何仍要探索以 gem5 为起点的 RTL 转化工作？核心原因在于架构研究的视角与生态复用：SystemC 通常聚焦于特定 IP 或子系统的建模与验证，而 gem5 提供了一套完整的计算机体系结构全系统研究框架——内置丰富的 CPU 微架构、多级 Cache 一致性协议、片上互连、PCIe/DRAM 模型以及完整的操作系统与驱动软件栈，使研究者能够在真实软件负载下快速开展端到端的架构探索。

3.1 用五大鸿沟标尺解剖 gem5

参照第 1、2 节建立的评估维度审视 gem5，可以清晰界定其能力边界与硬件综合级缺失：

1. 系统生态与抽象层	提供全系统软件栈（OS、驱动、真实工作负载）下的敏捷验证环境；基于 SimObject 实现高内聚的模块化快速迭代。	缺乏面向物理电路的综合子集定义，模型设计初衷完全面向宿主软件执行效率而非硬件映射。
2. 执行与并发模型	基于全局离散事件队列（Event Queue）按需调度事件，避免空拍计算，仿真速度远超 RTL。	事件回调函数默认零延迟顺序执行完毕，缺乏组合逻辑与时序逻辑的物理边界，无法直接映射为硬件并发流水线与数据通路。
3. 时序模型	通过预设时间戳调度未来事件，能够高效完成吞吐、带宽与访存延迟的宏观定量评估。	仅表达统计/事务级延迟，缺失周期精确（Cycle-Accurate）的握手、反压、气泡与逐拍状态机演进，也缺乏复位等硬件抢占语义。
4. 通信与内存模型	模块间通过 PacketPtr 指针零拷贝传递事务包，极大降低了软件建模与协议扩展复杂度。	深度依赖指针操作、动态堆内存分配与 STL 容器，严重违背硬件静态布线与隔离小存储器的要求，且不可直接做静态指针别名分析。
5. 数据类型与物理反馈	直接使用标准 C++ 数据类型，开发与软件调试门槛极低。	缺乏位精确（Bit-Accurate）数据位宽约束；完全缺失物理 PPA 反馈（面积、关键路径主频上限、动态/静态功耗），架构优化容易偏离物理可实现性。


上述诊断表明，试图开发一套工具将整个 gem5 源码库（含全局事件队列、PacketPtr 指针体系与全系统外设）无损直译为 Verilog，在语义上是不可行的，在工程上也是不必要的——正是因为 gem5 刻意选择了这些远离底层电路的软件抽象，才换来了极致的体系结构研究便利性。

因此真正需要解决的核心问题并非“全量编译 gem5”，而是消除架构级模拟器（gem5）与物理级实现（RTL）之间的双源码割裂（Dual-Model Gap）：如何在保留 gem5 全系统架构探索能力的前提下，针对定制硬件目标模块（如 Compute Tile、DMA/PCIe 控制器及片上 SRAM 等核心微架构单元），打通从 C++ 架构逻辑到可验证物理 RTL 的敏捷演进通路。

为此，无论后端采用何种转化引擎，第一步都必须确立清晰的分层隔离架构基线：

⚬ 不可转化层（gem5 隔离适配层 / Wrapper Layer）：驻留于 gem5 仿真框架侧，负责承接 gem5 的全局事件队列、时钟 Tick 驱动以及 SimObject 参数配置，并在边界处将 gem5 的 PacketPtr 指针事务与动态数据结构，拆包翻译为定长、无指针、具备明确握手语义的自定义内部事务/存储结构。
⚬ 可转化核心层（目标硬件微架构层）：剥离一切 gem5 框架依赖，仅通过隔离层定义好的受限端口与存储接口同外界交互，集中承载目标加速器（如 GW100）的真实计算与控制逻辑。

这一分层架构与我们现有代码库（如 Compute Tile 与 PCIe 模块中已有的 gem5 隔离层及相对独立的 GW100 核心逻辑）高度吻合，为后续的自动化转换与联合验证奠定了天然的工程边界。




## 4. 路线收敛：从规则驱动走向 Agent 驱动的可验证敏捷流程

综合前文对类 C 硬件建模、C++ 系统级设计和 gem5 生态的分析可以发现，现有技术已经分别解决了高层行为模型的仿真、硬件结构的构造、预 RTL 架构探索以及 RTL 在全系统环境中的集成问题。例如，OCAPI 实现了从 C++ 算法模型到周期精确、位精确架构模型，再到 RT-VHDL 的逐步细化；gem5+rtl 建立了 RTL 模块与 gem5 全系统仿真环境之间的连接；gem5-SALAM 则利用 LLVM IR 建立了可在 gem5 中执行的加速器模型。

这些工作为本项目提供了重要基础，但也提出了一个进一步的工程问题：对于已经存在于 gem5 中、并经过系统级负载验证的定制硬件模型，能否在保留其全系统架构探索能力的前提下，进一步提取出受规范约束的硬件核心，使其同时支持原生 C++ 仿真和 RTL 综合？

本项目不试图对完整 gem5 进行源码级自动翻译，而是采用分层解耦的方式，将 gem5 专有的事件调度、事务通信和系统配置机制保留在不可综合的适配层中，将目标模块中具有明确状态转移、固定数据位宽和静态接口的部分提取为共享硬件核心。在此基础上，建立 Native C++ 与 HLS/RTL 双后端，实现体系结构模拟和实际电路实现之间的协同演进。

进一步地，考虑到传统人工重构与规则驱动编译流程在复杂微架构迁移中存在较高的工程成本，本项目引入 Agent 辅助的语义重构机制。Agent 负责理解既有设计、按照硬件契约重构代码，并根据错误证据执行局部修复；确定性工具则负责静态约束检查、编译、仿真、综合、形式验证和 PPA 分析。

为保证多轮修改后的行为一致性，本项目在 gem5 隔离层边界记录系统级运行事务，构建具有版本和环境信息的工作负载 Trace 数据集，并利用这些数据对共享核心及生成 RTL 开展差分验证。通过首次行为分歧定位、无状态证据修复和版本化回归测试，形成从系统级架构探索到物理 RTL 实现的可验证细化闭环。

本项目最终关注的不是单纯提高 RTL 代码生成的成功率，而是在保留系统级架构探索效率的同时，降低硬件模型向可综合实现迁移的工程成本，并建立一套能够持续验证设计正确性和硬件实现质量的 Agent 辅助开发方法。

在确立了“隔离层 + 核心层”的架构基线后，核心问题聚焦为：采用何种技术引擎将可转化核心层的 C++ 逻辑推进至高质量、可信的物理 RTL？

4.1 传统规则驱动路线的盘点与工程瓶颈

围绕“如何把规范化的 C++ 核心转化为 RTL”，传统 EDA 与编译领域主要存在三条规则驱动（Rule-Driven）的技术路线：

⚬ 路线 A（规范化 C++ 子集 + 双后端适配）：通过宏或模板对核心层接口进行抽象，在 gem5 编译模式下退化为原生 C++ 结构体以零开销运行，在 RTL 综合模式下切换为 SystemC/HLS 原语（对接开源 Intel ICSC 或商业 Catapult C / Vitis HLS 等工具）生成 RTL

⚬ 路线 B（面向计算内核的编译器 IR 下沉）：借鉴 gem5-SALAM 与现代 MLIR/CIRCT 硬件编译基础设施的思路，将核心层 C++ 经 Clang 降级为 LLVM IR / MLIR，再通过标准硬件方言（如 handshake、calyx、hw/seq）完成自动调度、资源绑定与 SystemVerilog 生成。

⚬ 路线 C（结构构造型 C++ 包装）：借鉴第 2.2 节所述 Ocapi 的构造思想，将核心层拆分为“静态拓扑构造期”与“逐拍状态更新期”，构造期生成硬件网表，运行期直接供 gem5 驱动行为仿真。

规则驱动路线的优势在于100% 确定性与完全可复现——其全部映射逻辑均由人类编译专家通过静态语法分析、图调度与形式化算法预先写死。但面对需要频繁迭代的定制加速器体系结构研发，这三条路线都暴露出沉重的工程瓶颈：路线 A 强迫架构师按极其严苛的 HLS/RTL 子集手工重写全部业务逻辑，大幅削弱了敏捷性；路线 B 与路线 C 则需要投入极高的编译器 Pass 研发与维护成本，且一旦面对不规则控制流或非标准微架构代码，静态规则编译器极易报错或综合出低效电路。

4.2 范式转向：Agent 与确定性工具协同的混合敏捷流程

近年来，硬件前端设计正呈现出从“纯规则驱动”向“Agent 驱动 + 确定性工具兜底”的敏捷化范式迁移。例如，工业界（如 Cadence ChipStack AI Super Agent 提出的 Spec → C++ HLS → RTL 路线与共享心智模型）与学术界（如面向 C-to-Synthesizable-C 的证据驱动 LLM Agent 四段式验证闭环，以及探讨从“Vibe Coding”走向“可验证工程”的 Agentic Agile-V 方法学）的近期实践共同印证了一点：直接让大模型裸生成 Verilog 极不可靠；真正稳健的敏捷路径，是由 Agent 承担前端的模糊语义理解与代码重构，而由规则工具与仿真器充当后端的确定性裁判。

基于此趋势，本项目决定不重复造一个重型规则编译器，而是从开发流程与验证体系切入，聚焦于“人定架构边界 + Agent 承担语义重构与转译 + 规则工具与 gem5 仿真器充当确定性裁判”的混合范式。

在这一范式下，利用 Agent 产出一份“看起来能编译”的 RTL 并不困难；本项目真正需要攻克的工程难题，在于如何保证 Agent 产出的“结构稳定化”与多轮迭代中的“持续可靠输出”——即消除大模型的概率性漂移、防止修改破坏既有接口拓扑，并杜绝 Agent “自写自测”导致的验证盲区。


## agent 探索实验后的总结

基于 gem5 的模型通过宏或者简单的语法机制去实现双轨的后端实现不可能，在提取抽象 cpp 逻辑逻辑通过中介层进行接入在简单（例如 compute tile 中的 sync）构件中可以实现，但是在复杂的构建存在大量的问题。因此我们原来提到的路线 a：将 gem5 的已有建模通过简单修改就能实现硬件综合这条道路不可能。后面尝试了复用 systemc 的经验，使用类模板实现综合，同时对接 gem5，也就是说通过一个中间规范层去实现两个方向的对接。
