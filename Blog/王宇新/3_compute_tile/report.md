## 预研
这个阶段的工作在同目录下有两个 claude 的生成的文件，基本上能概括我的大致想法，我在这里只去去介绍一下我自己的思路，我的考虑点主要是下面几个：1 dma 是否有必要，2 在 decode 阶段如何解决带宽的一个问题，3 在 prefill阶段如何去解决竞争读取sram 的问题，4 外部接口的问题，5 ni 和 noc 网络构成的简单协议栈（这一部分没有深入了解，应该需要 dma 的参与）

这是一个很粗糙的设计方案，大致展现我目前的想法，dma 保留是为了在功能上更加清晰，本身在实际的硬件设计中是不是个好的方式并不确定，另外整体上原来 html 的方案并没有进行一个全部改写，而是基于原来的方案增添了一些机制，目前边界性或者说是具体的一个设计还没有定下来，只在总体上有一个架子

首先来考虑 decode 阶段，decode阶段主要是宽带上限，其中又主要是因为权重的搬运为瓶颈点（单用户短对话场景），而 NOC 包的搬运又主要是以 60B 为上限，因此我们从整体上考虑，主要是需要额外增加一个fifo队列，以实现单 tile 宽带的拉满。这是 decode 阶段的一个优化。

另一个阶段是 prefill 阶段。prefill 涉及大量 SRAM 的读写，并且可能会出现竞争。怎么在 SRAM 的上进行解决呢，类似于dram这样，把内存块进行分区，保证一种类型的请求只读取一个块，从而保证并发。这是我们添加的两个机制。

还有一个优化点是在矩阵引擎和向量引擎之间进行优化：将矩阵引擎的 FP32 板块抽出来，让向量引擎以前也可以去访问这个 FP32 板块。这样实现数据直接在寄存器层级进行沟通，而非在 SRAM 层级进行沟通。在特定的运行下，类似 swiGLU 的机制会优化很多。

另一个是接口侧的问题。很明显，我，门不可能使用单独的一条线去进行沟通，至少需要 request 和 response 两条线。至于具体的沟通线给出，其实我到现在还没有想明白到底是要放几条线，但是多线机制目前是定下来了。因此，我们在这里给出了一个很总体的大概架子，很多细节上的东西其实没有做很多。其实也还好，具体的问题可能要具体写的时候才能定下来


## 预研 2

和君泽聊了一下，现在给出调整设计的调整和思考。原先预想的一个设计是 compute tile 仅仅只做单独的数据的数据处理和数据流动，因此在整体上只去关注一个 decode 阶段的数据流向和 prefill 阶段的一个优化上的处理，预想上去处理一个多播和外部数据的一个控制主要是下面几个方面，一个是通过寄存器，一个是本身 dma 做特定数据步长等等的处理，因此这些的控制和设计要求将 sram 去抽象出来一个寄存器的地址结构或者增加一个额外的 ram，通过这种方式进行一个调节。

那么我们来看更新之后的要给思路，一个是将 dma 和 ni 结合在一起，我之前一直很犹豫要不要保留 dma，很长一段时间里面保留 dma 的原因就是在功能上很清晰，但是我本身忽略了一点，忽略了在理想情况下 dma 都远远不满，理想峰值 135gb，落到具体的 tile 只有不到 10gb，同时片上仅仅允许 60b 的包进行传递，这些问题是的 dma 放在这里完全是小题大做，根本跑不满，因此将本身 dma 承载的一个功能给到 ni 则是更应该进行的选择，而且也省略一个中间层。因此这一步在我的理解里是很自然的修改。

另一个就是增加 riscvfive 核进行控制，这个主要是设计决策的问题，将管理的部分给管理 tile 并将固定规则放到内部 tile 进行管理，还是增加 riscfive 核实现一个动态编程，讨论的结果是使用前者。就先按这种方式进行设计。

那么如果以这种机制，本身其他部分的管理压力就会小很多，实际上以这种方式进行统筹，sram 原来拆分成寄存器区域和一般地址区域完全没有必要，但是 tile 状态位还需要地方存放，是本身在 riscfive 核里面添加状态位还是再增加一个小 ram，这个应该进行考虑，添加 riscfive 核之后外部的接口就没必要设计的这么复杂，同时硬件同步器和 riscfive 核的关系应该理清楚，riscfive 核到底设计出来几个也需要理清楚。

## 初步实现
目前经过了几天的时间实现了 compute tile 的功能性实现，总体上打通了整条线路，将上面这么一个设计初步落地。先来介绍一下这一版实现了什么，第一将上满的整体架构的各个组件都进行了落地，并且通过简单的时序问题串联起来了整个项目实现了项目的数据通路打通，其中 sram 没有拆成具体的 bank，而是每 256b 进行换块。矩阵引擎只实现了 add mul simu 这三个简单算法，这里添加计算形式在代码逻辑上没有很困难，困难的是管理特定计算形式的内存读写，在这三种计算前提下 vector 的两个数据必然有一个来自于 sram，在添加了更多的计算形式后这一点是否成立还需要进行考虑，同时我们并没有接入真正的riscfive 核，而是使用了一个简单的 ctrl 状态机进行控制，保留中央控制核的设计，在这里整体数据流通的基本方式是，外部通过 access 和 windows 窗口进行访问，通过简单的时序完成内存访问的模拟，64b 数据包在 nidma 中实现转化并在 compute tile 内部实现大块数据（暂定 256b）的读写，因为这个原因没有复用公共抽象出来的 sram

这就是这一版的大致实现，稍后做的就是补充测试和将整体去接入一个实际的实现，初始化多个 tile

3. 具体计算指令的扩展，覆盖 example 模型的计算过程
4. riscfive 核真正接入，在哪一步接入应该是需要去考虑和设计的事情
5. 将大部分数据选项变得可配置化，通过具体的测试结果来选择到底使用哪一种
