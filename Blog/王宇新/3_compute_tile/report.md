这个 report 是用来去记录我在 compute tile 开发和设计的决策和修改吧

## 预研
这个阶段的工作在同目录下有两个 claude 的生成的文件，基本上能概括我的大致想法，我在这里只去去介绍一下我自己的思路，我的考虑点主要是下面几个：1 dma 是否有必要，2 在 decode 阶段如何解决带宽的一个问题，3 在 prefill阶段如何去解决竞争读取sram 的问题，4 外部接口的问题，5 ni 和 noc 网络构成的简单协议栈（这一部分没有深入了解，应该需要 dma 的参与）

因此在这里的设计实际上是基于前四个思路

这是一个很粗糙的设计方案，大致展现我目前的想法，dma 保留是为了在功能上更加清晰，本身在实际的硬件设计中是不是个好的方式并不确定，另外整体上原来 html 的方案并没有进行一个全部改写，而是基于原来的方案增添了一些机制，目前边界性或者说是具体的一个设计还没有定下来，只在总体上有一个架子

首先来考虑 decode 阶段，decode阶段主要是宽带上限，其中又主要是因为权重的搬运为瓶颈点（单用户短对话场景），而 NOC 包的搬运又主要是以 60B 为上限，因此我们从整体上考虑，主要是需要额外增加一个fifo队列，以实现单 tile 宽带的拉满。这是 decode 阶段的一个优化。

另一个阶段是 prefill 阶段。prefill 涉及大量 SRAM 的读写，并且可能会出现竞争。怎么在 SRAM 的上进行解决呢，类似于dram这样，把内存块进行分区，保证一种类型的请求只读取一个块，从而保证并发。这是我们添加的两个机制。

还有一个优化点是在矩阵引擎和向量引擎之间进行优化：将矩阵引擎的 FP32 板块抽出来，让向量引擎以前也可以去访问这个 FP32 板块。这样实现数据直接在寄存器层级进行沟通，而非在 SRAM 层级进行沟通。在特定的运行下，类似 swiGLU 的机制会优化很多。

另一个是接口侧的问题。很明显，我，门不可能使用单独的一条线去进行沟通，至少需要 request 和 response 两条线。至于具体的沟通线给出，其实我到现在还没有想明白到底是要放几条线，但是多线机制目前是定下来了。因此，我们在这里给出了一个很总体的大概架子，很多细节上的东西其实没有做很多。其实也还好，具体的问题可能要具体写的时候才能定下来
