# Compute Tile 设计的推理链：从硬件数字和数据流到方案

> 2026-11-04 · Claude 按本人 CT0–CT3 的思路和讨论整理 · 方案本身见 [`ARCHITECTURE.md`](ARCHITECTURE.md) · 数字的完整算式见 `03_COURSE/CT_TILE/CT2_NUMBERS.md`
> 所有数字都是**推算**（按峰值、均匀分布），没有跑过模拟。

## 0. 一句话

GW100 decode 时，每个 token 要把约 0.7–0.9 GB 权重从设备内存搬进 16 个 Compute Tile，计算只要几十纳秒，搬运要几毫秒。所以 Compute Tile 首先是一个**接住数据流的部件**，其次才是计算部件。下面每一个设计决定，都是从这个事实一步一步推出来的。

## 2. 起点：两组数

**硬件**（spec-arch、spec-address-map v0.1；旧参数草案）

| 量 | 值 |
|---|---|
| 设备内存峰值 | 136.5 GB/s（8 通道，按 256 B 交织到 4 个 Memory Tile） |
| NoC 一条链路 | 64 B/周期 = 64 GB/s（1 GHz） |
| 一次 NoC 请求 | ≤ 64 B，往返上限 1 µs |
| Compute Tile | 16 个，每个 SRAM 2 MiB、矩阵引擎 2048 乘加/周期 |
| SRAM（旧草案） | 32 bank × 32 B = 1024 B/周期 |

**负载**（Qwen2.5-0.5B，BF16，生成一个 token）

| 数据 | 量 |
|---|---|
| 24 层权重 | 682.5 MiB |
| lm_head | 259.7 MiB |
| KV 读（S = 1024） | 12 MiB |
| Tile 间激活 | 约 5.5 MiB |
| 指令、同步 | KiB 级 |

## 3. 每一步推导

### ① decode 的瓶颈是权重流入

- 权重一行比其余所有行加起来大几十倍。
- 时间上限：682.5 MiB ÷ 136.5 GB/s ≈ 5.2 ms（加 lm_head 7.2 ms）。
- 一个 Tile 的那份 q_proj：搬 98 KiB 要 11.8 µs，算只要 25 ns，**慢 500 倍**。
- 矩阵引擎利用率 4.3 ÷ 2048 ≈ 0.2 %；SRAM 利用率约 1.7 %。

**推出**：Tile 设计的第一目标是让权重**不断流**，不是加快计算。

**这一步依赖的假设**：单用户、短上下文。LLaMA2-7B 没有 GQA，S ≈ 6,700 时 KV 读就追上权重；那时“KV 怎么流”会和权重同等重要。

### ② 谁发读请求

- 地址交织使每个 Tile 的顺序读自动分散到 4 个 Memory Tile，**Tile 不需要选“走几条内存线”**。
- 如果一个中央发起方发全部读请求、数据回到它那里：它只连一个路由器，入口一条链路 64 GB/s，**最多拿到 136.5 的一半**。
- 每个 Tile 各发各的：每个 Tile 只要 8.5 GB/s，每 7.5 周期发一个请求；最忙的是 Memory Tile 出口第一段，34.1 GB/s（53 %）。
- 调研里的几家（M100、AMD、Tenstorrent）都是每个计算单元有自己的发起方。

**推出**：Tile 自己发请求（CT3 的做法 A）。

### ③ 64 B 请求 → 在途队列 → 保留 DMA

- 请求最大 64 B，而往返要几百到一千个周期。只发一个、等回来再发下一个，带宽只有 64 B ÷ 1000 周期 ≈ 0.064 B/周期，差 130 倍。
- Little 定律：在途请求数 = 带宽 × 延迟 ÷ 请求大小 = 8.5 × 1000 ÷ 64 ≈ **133**（延迟 200 周期时约 27）。
- 要有一个部件同时追踪这么多请求：发出、数响应、按地址放回、全回来后通知。

**推出**：这件事足够复杂，值得一个专门的部件，**保留 DMA**。本人在 CT1 倾向去掉 DMA（“16 个太贵、功能单一”），在 CT3 算清这一步后推翻了原来的倾向。

### ④ DMA 和 NI 分层

- DMA 管“一次搬运”：多维地址展开、在途队列、完成计数。
- NI 管“一个包”：打包成 ≤ 64 B、不跨 256 B、区间检查、隔离。
- NoC + NI 是一个简单的片上协议栈，NI 是协议转换器（本人 CT3）。

**推出**：功能分层清楚；性能是否需要合并，留到第二阶段测。

### ⑤ 从数据流推出对外接口

本人在 CT2 改了课程顺序：先定内部数据流，再定接口。按这个顺序，接口就是“框图上每一条跨出 Tile 的箭头”：

| 跨框的数据流 | 消息 |
|---|---|
| 指令进来 | #1 张量级指令 |
| 权重、激活被 DMA 拉进来 / 结果推出去 | #2、#3 DMA 读写 |
| 别的 Tile 的 DMA 来读写本 Tile | #4 |
| 别的 Tile 通知“数据好了” | #5 写同步计数器 |
| 本 Tile 告诉管理 Tile“做完了 / 出错了” | #6 写事件寄存器 |
| 固件查状态 | #7 读寄存器区 |
| 复位、隔离 | CRC 边带 |

再加一条约束：如果响应排在请求后面，两个 Tile 互相等对方的响应时会死锁。**推出**：请求、响应、指令分三类报文，各自排队（本人 CT3：“不可能只有一个接口，要 2–3 个”）。

### ⑥ prefill 时 SRAM 的读写

- prefill 时矩阵引擎吃 96 B/周期，向量引擎 32 lane × 两读一写约 384 B/周期，DMA 约 64 B/周期，合计约 544 B/周期，SRAM 有 1024 B/周期。**总量够，冲突在局部**：不同部件撞同一组 bank 时要排队。
- 本人方案：SRAM 分 16 组，权重、激活、结果放不同组。要做到这一点，编址要按地址高位分组，不能按 32 B 交织。
- SwiGLU 一类“矩阵乘完马上逐元素”的运算，结果写回 SRAM 再读出来是多余的一来一回。本人方案：矩阵引擎的输出直接流进 FP32 后处理。这是融合，第一版预留。

### ⑦ 生产者和消费者之间的同步

- 规格的释放语义：先写完、fence，再通知；消费者等到通知才读（spec-address-map §6.3 规则 8）。
- 只增计数器解决“数据好了没有”；双缓冲还要“空位还回来没有”，需要第二个反方向的计数器，或者 CB 那样的读写指针。
- 本人：两种都实现，跑实验比较。

## 4. 本人想法的变化（CT0 → CT3）

| 话题 | 一开始 | 后来 | 改变的原因 |
|---|---|---|---|
| Tile 是什么 | “一个小处理器，只靠外部接口通信” | 一个接住数据流的部件，内部由 DMA、SRAM、计算引擎组成 | CT2 的流量表 |
| DMA | 去掉：16 个太贵、只是搬权重 | 保留：要维护几十到上百个在途请求 | ③ 的 Little 定律 |
| 瓶颈 | KV cache 读最大 | 单用户短对话时权重加载最大 | CT2_NUMBERS 的表 |
| SRAM | 担心多模块同时读写成瓶颈 | decode 不是问题；prefill 时分组解决局部冲突 | ① 和 ⑥ 的带宽数 |
| 课程顺序 | 先定接口 | 先定内部数据流，再推接口 | 本人的判断：接口要从数据流推出来 |
| 对外接口 | 只想到“别人的读写、计数器、报告” | 7 种消息 + 三类报文 | CT3 §1 的清单 |

## 5. 这条链上最弱的几环

1. **峰值假设**：136.5 GB/s 是引脚上的理想值，实际可能只有六到七成（调研里 M100 推算约 67 %）。不改变结论，但所有余量都要打折。
2. **延迟未知**：在途请求上限 27 和 133 差了 5 倍，取决于 `spec-noc` 还没写的典型延迟。
3. **切分方式**：激活 5.5 MiB 是按“每个矩阵按输出列切 16 份”算的；换一种切法，Tile 间流量会变。
4. **模型选择**：结论 ① 对 Qwen 和 Llama-3.2-1B 成立；对 LLaMA2-7B 长上下文要重算 KV。
5. **SRAM 分组的代价没算**：分 16 组后，一组只有 1/16 的 bank 带宽。一个部件独占一组时够不够，要按每个部件的带宽单独核。
