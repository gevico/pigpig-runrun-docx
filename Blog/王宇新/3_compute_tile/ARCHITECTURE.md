## 1. 范围和设计点

### 1.1 Compute Tile 管什么

- 执行管理 Tile 派来的张量级指令，指令可以多播到多个 Tile。Tile 内没有通用处理器。【规格】spec-arch §2.3
- 计算部件（矩阵引擎、向量引擎）只读写本 Tile SRAM；Tile 和外面的数据交换全部由 DMA 经 NoC 显式完成。【规格】spec-arch §2.1
- 第一版按完整规格做，包括多播和本地窗口，不为“只有一个 Tile”做简化。【本人】CT1 Q1.2

### 1.2 设计点

| 阶段 | 瓶颈 | 对 Tile 的要求 | 来源 |
|---|---|---|---|
| decode（单用户、短上下文） | 权重从设备内存流进来的速度 | 让权重**不断流**：一块还在算，下一块已经在路上 | 【本人】CT3 总结 ①；数字见 CT2_NUMBERS §2、§4 |
| prefill | 矩阵引擎的算力；向量引擎和矩阵引擎频繁读写 SRAM | SRAM 多个部件同时读写不互相阻塞 | 【本人】CT3 总结 ①、⑤ |

- 设计用的模型：Qwen2.5-0.5B 做算术，GW100 主要负载 LLaMA2-7B 做校核。【TBD】本人还没定以哪个为准、多长上下文（批改 Q2.2）。
- 当前阶段只做功能验证，融合和性能优化预留、不实现。【规格】项目约定（`02_NOW/ACTIVE_TASK.md`）

## 2. Tile 在芯片里的位置

| 项 | 值 | 来源 |
|---|---|---|
| 个数、位置 | 16 个，Mesh 第 1–4 列 | 【规格】spec-arch §3.1 |
| 编号 | `ct = y × 4 + (x − 1)` | 【规格】spec-clock-reset-power §1.2 |
| 窗口 | 编号 `n = y × 8 + x`，基址 `0x10_0000_0000 + n × 16 MiB`；前 8 MiB SRAM 区（实际 2 MiB），后 8 MiB 寄存器区 | 【规格】spec-address-map §4.1–§4.2 |
| 本地窗口 | Tile 内部访问 `0x20_0000_0000 + o` = 本 Tile 窗口偏移 o；不出现在 NoC 上 | 【规格】spec-address-map §4.3 |
| 时钟 | `clk_core`，1 GHz，和 NoC 同一个时钟域 | 【规格】spec-clock-reset-power §2.1 |
| 复位、门控 | 由 CRC 控制，复位或关时钟之前必须先 NI 隔离 | 【规格】spec-clock-reset-power §4.5 |

例：坐标 (2, 1) 的 Tile，`ct = 5`、`n = 10`，SRAM `[0x10_0A00_0000, 0x10_0A20_0000)`，寄存器区 `[0x10_0A80_0000, 0x10_0B00_0000)`。

## 3. 内部结构

### 3.1 框图

```text
                       NoC（本位置的路由器）
                ┌─────────┬─────────┬─────────┐
                │ 请求类   │ 响应类  │ 指令类   │   三类报文，各自排队
  ┌─────────────┴─────────┴─────────┴─────────┴──────────────────────┐
  │                          NI（协议转换）                           │
  │   打包/拆包 ≤64 B · 执行期区间检查 · NI 隔离 · target 端译码      │
  └──────┬───────────────────────┬──────────────────────┬────────────┘
         │ DMA 的读写请求/响应     │ 别人对本 Tile 的读写   │ 指令
         ▼                       ▼                      ▼
  ┌──────────────┐        ┌──────────────┐       ┌──────────────┐
  │     DMA      │        │  寄存器区     │       │   控制器      │
  │ 多维地址展开  │        │ 状态/错误/    │◀──────│ 指令队列、    │
  │ 在途请求队列  │        │ 同步计数器    │       │ 译码、分发    │
  │ 完成计数      │        └──────┬───────┘       └──┬───┬───┬───┘
  └──────┬───────┘               │ 计数器            │   │   │  按单元分发
         │ 写入 / 读出             ▼                  ▼   ▼   ▼
  ┌──────┴────────────────────────────────────────────────────────┐
  │              SRAM 2 MiB，按地址高位分成 16 组                    │
  │   [ 权重缓冲 A | 权重缓冲 B | 激活 | 中间结果 | …… ]              │
  └──────┬─────────────────────────────────────┬──────────────────┘
         │ 激活 32 B/周期 + 权重 64 B/周期        │ 约 384 B/周期
         ▼                                      ▼
  ┌──────────────┐   结果直接流入（预留）   ┌──────────────┐
  │   矩阵引擎    │ ───────────────────────▶ │ FP32 后处理   │──▶ SRAM
  │ 8×64×dot4    │                         │ 流水 / 向量引擎│
  └──────────────┘                         └──────────────┘
```

### 3.2 部件

| 部件 | 职责 | 对应旧 main | 来源 |
|---|---|---|---|
| **NI** | 片上协议栈的一层：把 DMA 的一次搬运翻译、拆成 ≤ 64 B 的 NoC 包，收包还原成读写；执行期区间检查；NI 隔离；对外分三类报文 | 无（旧 main 用 `NoncoherentXBar` 直连） | 【本人】CT3 总结 ⑨⑩；区间检查、隔离【规格】 |
| **DMA**（规格叫 Data Mover） | 一次搬运的全过程：4 维 size/stride 地址展开；维护**在途请求队列**把带宽打满；数清响应，完成后按指令加同步计数器 | `DmaEngine` | 【本人】CT3 总结 ③④ |
| **控制器** | 接收指令、排队、译码，分给 DMA / 矩阵 / 向量；处理只做同步的指令；判定“本 Tile 程序结束”并报告 | `TileController` | 【推断】本人没单独讨论，按规格“集中派发”必须有 |
| **SRAM** | 2 MiB，所有部件之间的枢纽；按地址高位分 16 组，权重、激活、中间结果放不同组，边读边写不竞争 | `BankedSram`（32 bank × 32 B，交织） | 【本人】CT3 总结 ⑤；“按高位分组”是【推断】（批改 ⑤） |
| **矩阵引擎** | 矩阵乘（含 GEMV） | 旧 main 未实现 | 【规格】spec-arch §3.2；参数沿用草案 |
| **FP32 后处理 / 向量引擎** | 逐元素、归约、非线性（SiLU、exp、rsqrt）；矩阵引擎的输出可以直接流进来（SwiGLU 等），不回 SRAM | `VectorEngine` | 【本人】CT3 总结 ⑥；“在 Tile 内部”是【推断】（批改 ⑥ 理解 a）；直接流入属于融合，**第一版预留不做** |
| **同步计数器** | 只增计数器，等待“≥ N”；别的 Tile 可以写 | `SyncUnit` | 【规格】spec-address-map §5.2；是否加 CB 式的反向计数【TBD】（§8） |
| **寄存器区** | 状态、错误、计数器、队列状态 | 无 | 【规格】要放的内容；布局【TBD】（§5.3） |

## 5. 对外接口

### 5.1 物理口

只有两个：**NoC 口**（经 NI 接本位置的路由器）和 **CRC 边带**（`CT_RST`、`CT_CLK_EN`、`CT_ISO`、`ISO_ACK`、`ISO_FAIL` 各一位）。同步、事件、寄存器访问都是 NoC 上对特定地址的读写。【规格】spec-arch §4、spec-clock-reset-power §4.5、§6

### 5.2 NoC 口上的报文类别和消息

报文分三类，各自排队，互不阻塞；请求和响应必须分开，否则两个 Tile 互相等会死锁。【本人】CT3 总结 ⑨；指令类独立【规格】spec-arch §4

| # | 消息 | 类别 | 方向 | 对面 | 字段摘要 | 完成 / 出错 | 来源 |
|---|---|---|---|---|---|---|---|
| 1 | 张量级指令 | 指令 | 入 | 管理 Tile（可多播） | 一条指令；isa-v0 是 128 B = 2 个 64 B 包 | 先预留队列空位再送达；非法指令 → Tile 进入错误状态 | 格式【TBD】（`spec-isa`） |
| 2 | DMA 读 | 请求 → 响应 | 出 → 入 | Memory Tile / 别的 Tile | 40 位 DPA、长度 ≤ 64 B、不跨 256 B | 每个请求一个响应 OK / REJECT / FAULT；REJECT → Tile 错误状态 | 【规格】address-map §6 |
| 3 | DMA 写 | 请求 → 响应 | 出 → 入 | Memory Tile / 别的 Tile SRAM / 管理 Tile 事件寄存器 | 同上 + 数据、字节使能 | 同上 | 【规格】 |
| 4 | 别人读写本 Tile SRAM | 请求 → 响应 | 入 → 出 | 管理 CPU、HDMA、别的 Tile 的 DMA | 同 #2、#3，本 Tile 当 target | 本 Tile 回 OK / REJECT | 【规格】address-map §5.2 |
| 5 | 写本 Tile 的同步计数器 | 请求 → 响应 | 入 → 出 | 别的 Tile | 一次写；“加 1”还是“置值”【TBD】 | OK；计数器编号越界 → REJECT | 位置和语义【TBD】（`spec-tile-sync`） |
| 6 | 结束 / 出错报告 | 请求 → 响应 | 出 → 入 | 管理 Tile 事件寄存器 `TILE_EVT[ct]` | 一次写，置一位 | 置位不排队，原因在本 Tile 寄存器区 | 位的约定【推断】：第 ct 位对应第 ct 个 Tile |
| 7 | 读本 Tile 状态 | 请求 → 响应 | 入 → 出 | 管理 CPU | 读寄存器区 | — | 布局【TBD】（§5.3） |

### 5.3 寄存器区（最小集，【推断】，偏移相对寄存器区起点 `窗口基址 + 0x80_0000`）

| 偏移 | 名字 | 谁能访问 | 作用 |
|---|---|---|---|
| 0x0000 | `CT_STATUS` | 管理 CPU 读 | 空闲 / 运行 / 错误 |
| 0x0008 | `CT_ERR_CODE` | 管理 CPU 读、写 1 清 | 出错原因：非法指令、DMA 收到 REJECT、计数器越界…… |
| 0x0010 | `CT_ERR_INFO` | 管理 CPU 读 | 出错指令的序号、出错地址 |
| 0x0020 | `CT_QUEUE_LEVEL` | 管理 CPU 读 | 各单元队列里有几条指令 |
| 0x0028 | `CT_DMA_INFLIGHT` | 管理 CPU 读 | 在途请求数（NI 隔离时判断能不能复位） |
| 0x1000 + 4 × i | `CT_SYNC_CNT[i]` | 管理 CPU 读写；别的 Tile 只写 | 同步计数器，个数【TBD】（旧草案 32 个） |

## 6. 队列和缓冲

按建模规矩，每个队列写来源、消费者、容量参数、满了怎么办。【本人】CT0 Q0.7 + 批改补的两格

| 队列 / 缓冲 | 谁放 | 谁取 | 容量参数 | 满了怎么办 |
|---|---|---|---|---|
| 每单元指令队列 | 管理 Tile（经控制器） | DMA / 矩阵 / 向量 | `ct.inst_queue_depth`（旧草案 16） | 管理 Tile 预留不到空位就不发 |
| DMA 在途请求表 | DMA | NI 收到的响应 | `ct.dm_max_outstanding` | DMA 停止发新请求 |
| NI 发送队列（每类报文一个） | DMA、控制器 | NoC | `ct.ni_tx_depth` | 反压给 DMA |
| NI 接收队列（每类报文一个） | NoC | 控制器、SRAM、寄存器区 | `ct.ni_rx_depth` | 反压给 NoC（NoC 保证不死锁） |
| 权重双缓冲 A / B | DMA | 矩阵引擎 | 由编译器在 SRAM 里划分 | 用同步计数器保证不覆盖（§8） |

**在途请求表要多深**（批改 ③）：在途数 = 带宽 × 往返延迟 ÷ 64 B。每 Tile 8.5 B/周期，延迟上限 1 µs = 1000 周期 → 约 133；延迟 200 周期 → 约 27。旧草案 32 只够 240 周期。

## 7. 两条数据流

### 7.1 decode：一个 Tile 算 q_proj 的 1/16

```text
1. 管理 Tile ─指令─▶ 控制器          （多播给 16 个 Tile；SRAM 地址写本地窗口）
2. 控制器 ─▶ DMA：搬权重 98 KiB       DRAM（交织，4 个 Memory Tile）→ SRAM 权重缓冲 A
                                      在途 ≈ 27–133 个 64 B 请求，约 11.8 µs
3. 控制器 ─▶ DMA：搬输入激活 1.75 KiB   别的 Tile 或 DRAM → SRAM 激活区
4. DMA 数满响应 ─▶ 计数器 c0 += 1
5. 矩阵引擎 等 c0 ≥ 1 ─▶ 读 SRAM、算（约 25 周期）─▶ 写 SRAM 结果区 112 B
   同时 DMA 已经在往缓冲 B 搬下一块权重
6. DMA 把结果写到下一步的消费者；写完收齐响应 ─▶ 再加计数器 / 写事件寄存器
   （顺序：先写完、再通知；address-map §6.3 规则 8）
```

### 7.2 prefill：权重复用 S 次

权重进 SRAM 一次，矩阵引擎按激活 32 B/周期 + 权重 64 B/周期跑满；结果流进 FP32 后处理（预留）或写回 SRAM 给向量引擎。SRAM 上合计约 544 B/周期，占 1024 B/周期的一半多。分组的目的：权重组、激活组、结果组各自的读写不撞同一组 bank。

## 8. 待决事项

| 事项 | 当前默认 | 怎么决定 |
|---|---|---|
| 同步机制：只增计数器 / CB 式双向计数 | 只增计数器 + 编译器配反向计数器 | 本人：两种都做，跑实验比（实验设计待写，CT3 Q3.7） |

| ≤ 64 B 拆分放在 DMA 还是 NI | NI（按本人“NI 是协议转换器”） | 本人确认 |
| 在途请求上限 | 133（按 1 µs 最坏延迟） | 等 `spec-noc` 给出典型延迟 |
| FP32 后处理是 Tile 内部还是跨 Tile 共享 | Tile 内部 | 本人确认（跨 Tile 和 spec-arch §2.1 冲突） |
| 设计点模型和上下文长度 | Qwen2.5-0.5B 短上下文 | 本人定；LLaMA2-7B 在 S ≈ 6,700 时 KV 追上权重 |
| 指令格式 | 沿用 isa-v0 128 B | `spec-isa` |
